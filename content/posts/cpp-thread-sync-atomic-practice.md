> 数组还活着，不代表现在就能读；每一步都是原子操作，也不代表组合起来就能算对。

在[第一次 C++ 编程练习](/posts/cpp-raii-first-practice/)里，我通过构造与析构理解 RAII；在[练习 2～5](/posts/cpp-ownership-borrowing-chunked-practice/)里，我继续练习所有权、移动语义、函数借用和数组分块。

当时最常问的是：**谁拥有这块内存，借用什么时候失效？**

练习 6 开始，同一块数组交给了不同线程。这时只追踪所有权已经不够，还要问：谁在访问哪些元素，什么时候可以读取另一条线程的结果？到了练习 9，我又发现，即使所有访问都用上了原子操作，计算仍然可能出错。

这篇继续沿着实际练习复盘，保留当时的判断、追问与修正。正文展示关键片段，文末附根据对话整理的完整源码；错误示例会单独标明。

## 1. 四次练习在解决什么

| 练习 | 实际做的事情 | 新增的问题 |
|---|---|---|
| 6 | 工作线程和主线程分别给半段数组加 10 | 区间不重叠以后，为什么还要等待？ |

这些练习都在 CPU 上使用 C++17，没有进入 CUDA，也没有做性能基准测试。这里的目标是把正确性和同步关系解释清楚。

## 2. 练习 6：分好了数组，还要分清时间

### 2.1 `n = 1` 时，我把分工说反了

核心代码很短：

```cpp
void add_parallel(int* data, std::size_t n, int delta) {
    if (n == 0) return;
    const std::size_t mid = n / 2;
    std::thread worker(add_inplace, data, mid, delta);
    add_inplace(data + mid, n - mid, delta);
    worker.join();
}
```

`add_inplace` 只是遍历前 `n` 个元素并执行 `data[i] += delta`。工作线程收到的是指针值的副本，没有复制数组，也没有接管所有权。

我写对了后半段的起点和长度，却问：

> “当n=1时,工作线程处理一个元素,主线程不处理?”

实际恰好相反。`1 / 2` 的整数结果是 `0`，因此工作线程处理空区间，主线程处理那个元素。

| `n` | `mid` | 工作线程索引区间 | 主线程索引区间 |
|---|---:|---|---|
| 0 | 0 | 不创建线程 | 直接返回 |
| 1 | 0 | `[0, 0)` | `[0, 1)` |
| 9 | 4 | `[0, 4)` | `[4, 9)` |
| 10 | 5 | `[0, 5)` | `[5, 10)` |

这让我继续保留上一轮的习惯：不要只看“前半段、后半段”这些描述，要把边界代入。奇数长度、单元素和空数组，往往最能暴露理解是否准确。

### 2.2 生命周期正确与访问同步正确，是两件事

如果工作线程仍在使用借用指针，主线程却提前执行 `owner.reset()`，数组就会被释放，线程再访问它就是释放后使用。这里释放的是数组，`owner` 对象本身仍然存在。

对话中我曾把 `reset()` 打成了 `get()`，随后明确纠正了笔误。这两个操作的区别仍需记牢：`get()` 只取得借用指针，`reset()` 才会释放当前管理的资源。

但即使不释放数组，提前读取工作线程正在修改的元素也不安全。我当时的解释是：

> “在join()前读取元素也不安全,因为读到的数据的版本可能不对,造成错读?”

需要修正的是“版本可能不对”这个说法。不同线程对同一内存位置存在冲突访问，至少一方写入，且没有适当的同步关系、访问也不是适当的原子访问时，就可能构成 **data race（数据竞争）**，行为未定义。不能把它理解为只会读到修改前或修改后的值。

反过来，`join()` 前也不是所有读取都被禁止。例如，主线程已经处理完自己的后半段，工作线程只访问前半段，此时读取后半段不涉及同一元素的冲突访问。

**关键不在于“还有线程运行”，而在于具体访问是否冲突、是否有同步保证。**

`join()` 成功返回，既表示目标线程已经结束，也建立相应的同步关系，使当前线程后续能够观察目标线程此前的写入。这可以对照 [C++ 标准工作草案的 `join()` 说明](https://eel.is/c++draft/thread.thread.member)阅读。

### 2.3 验证代码本身也需要检查

我加入了 `n = 100000` 的测试。每个元素从 `i` 变成 `i + 10`，总和为 `5,000,950,000`，已经超出常见的 32 位有符号整数范围，所以累加器用了 `long long`。

原先的验证公式直接写 `n * (n - 1) / 2 + 10 * n`，而 `n` 是无符号的 `std::size_t`。空数组时 `n - 1` 会回绕。整理版在本练习的小规模输入范围内先转换：

```cpp
const long long count = static_cast<long long>(n);
assert(total == count * (count - 1) / 2 + 10 * count);
```

除了总和，还逐元素核对，避免两个错误恰好抵消。这里的类型调整适用于练习规模，不能据此承诺任意大输入都不会溢出。

## 3. 练习 7：分别计算，等待以后再合并

这一轮不修改数组，而是只读借用：

```cpp
long long sum_parallel(const int* data, std::size_t n) {
    if (n == 0) return 0;
    const std::size_t mid = n / 2;
    long long left = 0;

    std::thread worker([&] {
        left = sum(data, mid);
    });
    const long long right = sum(data + mid, n - mid);
    worker.join();
    return left + right;
}
```

这里的 `[&]` 让 lambda 通过引用访问所需的外部变量。它没有延长被引用对象的生命周期；这些局部变量之所以在工作线程使用期间仍有效，是因为函数在返回前执行了 `join()`。

我当时用自己的话解释：

> “在一个线程中,代码是顺序执行的,在需要使用right的时候,right肯定已经计算完成了,但是不同线程之间的执行时间不确定”

更准确地对应到代码：主线程必须先完成 `right` 的初始化，才执行后面的合并；而 `left` 由工作线程写入，需要通过 `join()` 建立完成与同步的保证。

我还分析了另一种写法：先 `join()`，再算 `right`。结果仍然正确，但主线程计算后半段时，工作线程已经结束，两段求和失去了重叠执行的机会。

因此这里的等待位置是：**先完成本线程能独立做的计算，再等待，最后读取并合并另一线程的结果。** 这只是保留并行机会，实际是否更快还取决于数据规模、线程创建开销和调度，不能只凭代码中出现了两个线程就下结论。

这次我在本地拿到了预期结果和 `PASS`。相比练习 6，我开始能用线程内的顺序和线程间的同步解释代码。

## 4. 练习 8：`lock_guard` 把 RAII 接到了锁上

### 4.1 我理解锁，却没理解这一行声明

练习 7 让两个线程分别写 `left`、`right`，等待后统一合并。练习 8 改为两个线程都更新一个共享的 `total`：

```cpp
void accumulate_chunk(const int* data, std::size_t n,
                      long long& total, std::mutex& mutex) {
    const long long local = sum(data, n);
    {
        std::lock_guard<std::mutex> guard(mutex);
        total += local;
    }
}
```

我已经熟悉其他语言中锁的用途，但疑惑：为什么 C++ 只是声明 `std::lock_guard<std::mutex> guard(mutex);`，就能达到加锁的效果？

答案又回到了第一篇的对象生命周期：`guard` 是局部对象，构造时调用这把锁的 `lock()`，离开作用域析构时调用 `unlock()`。这正是 [标准草案对 `lock_guard` 的规定](https://eel.is/c++draft/thread.lock.guard)。

| 对象 | 管理的资源或状态 | 生命周期结束时 |
|---|---|---|
| `unique_ptr<int[]>` | 动态数组的所有权 | 释放所管理的数组 |
| `lock_guard<mutex>` | 互斥锁的持有状态 | 解锁 |

因此，那一行声明有实际行为。它把获得锁与释放锁绑定到了对象的构造、析构上，也让正常的异常展开路径能够释放锁。

### 4.2 锁不会自动识别它保护哪个变量

`mutex` 并不知道 `total` 是谁。正确性来自访问者共同遵守约定：需要互斥的冲突访问使用同一把锁。

下面是**错误示例**：

```cpp
{
    std::lock_guard<std::mutex> guard(mutex);
} // 已解锁
total += local; // 两个线程这样做，仍可能发生数据竞争
```

保护范围取决于 `guard` 的生命周期，不取决于 `mutex` 变量是否还存在。最终在主线程 `join()` 之后读取 `total` 则可以依靠线程完成后的同步，不必机械地认为每次读取都必须再加锁。

另一种修改是把 `sum(data, n)` 也放到锁里面。这样结果可以正确，但两个线程争用同一把锁，原本可独立进行的只读求和也被串行化。

我给出的判断是：

> “这样结果也正确,但是会导致锁的范围太大”

所以本练习选择：**锁外计算局部和，锁内只合并共享总和。** 前提是求和期间数组没有其他写入者。

### 4.3 TSan 的 `FATAL`，把我带到了运行环境

功能测试通过后，我尝试用 ThreadSanitizer 检查数据竞争，却遇到了：

```text
FATAL: ThreadSanitizer: unexpected memory mapping 0x5d31c4cfc000-0x5d31c4cfe000
```

这与 `WARNING: ThreadSanitizer: data race` 不是同一种报告。工具在内存映射方面失败，不能据此认定代码有数据竞争，也不能把它当成检测通过。

当时的环境记录是 GCC 13.3.0、WSL2 内核 `6.6.87.2-microsoft-standard-WSL2`，`randomize_va_space` 为 `2`，`vm.mmap_rnd_bits` 为 `32`。

排查时，我临时将 `vm.mmap_rnd_bits` 从 `32` 调成 `28`，重新运行已有的 TSan 程序，得到：

```text
n=0, sum=0
n=1, sum=-3
n=9, sum=-5
n=10, sum=-6
n=1000, sum=-3
PASS
```

随后立即恢复到原值 `32`。这是当时的实验记录，不是运行这些例程的常规前置要求，也不能推广为所有 TSan 报错的修复方案。调整这个系统参数会改变地址随机化强度，不应照搬成永久配置。

`vm.mmap_rnd_bits` 控制相关内存映射地址随机偏移使用的位数，并不改变 RAM 容量，也不是把进程改成 28 位地址。可参考 [Linux 内核参数文档](https://docs.kernel.org/admin-guide/sysctl/vm.html#mmap-rnd-bits)。[LLVM 的 TSan 文档](https://clang.llvm.org/docs/ThreadSanitizer.html)也说明了工具需要额外的虚拟地址空间并存在平台限制。

结合调整后能够运行的现象，我把当时的问题定位到与地址布局有关的工具环境兼容性；这仍是基于该次实验的判断。本次测试没有报告数据竞争，也不等于证明所有执行路径都不存在问题。

这一段还提醒我：指导过程里曾把 `n=9`、`n=10` 的预期结果写成 `-3`，实际应为 `-5`、`-6`。程序用 `i % 7 - 3` 初始化，每七项和为零，剩余 `r = n % 7` 项的和才是 `r * (r - 1) / 2 - 3 * r`。验证程序和预期输出同样需要复核。

## 5. 练习 9：没有 data race，结果也可能不对

### 5.1 `fetch_add` 把读、改、写连成一个原子操作

两个线程各完成 `jobs` 次计数：

```cpp
void count_jobs(std::atomic<long long>& counter, int jobs) {
    for (int i = 0; i < jobs; ++i) {
        counter.fetch_add(1);
    }
}
```

工作线程与主线程都使用同一个 `counter`。主线程完成自己的计数后等待工作线程，再 `load()`，预期结果为 `2LL * jobs`。本练习沿用默认内存序，没有进一步展开不同内存序的选择。

关键区别出现在下面这个**逻辑错误示例**：

```cpp
const auto old = counter.load();
counter.store(old + 1);
```

`load()`、`store()` 各自原子，但它们之间可以穿插另一线程的操作：

| 顺序 | 线程 A | 线程 B |
|---|---|---|
| 1 | 读到 0 | |
| 2 | | 读到 0 |
| 3 | 写入 1 | |
| 4 | | 写入 1 |

两次计数最后只增加了 1。这种丢失更新不需要发生未定义行为就能出现；默认的顺序一致性也不会自动把两次独立操作合成一个整体。`fetch_add` 则提供一次完整的原子读改写，参见 [标准草案的原子整数操作说明](https://eel.is/c++draft/atomics.types.int)。

### 5.2 我最需要修正的是术语背后的判断

我起初说，两步之间“还是会出现数据竞争”。后来通过对照实验，修正为：

- **data race**：本例中对计数器的访问都是原子操作，不存在由这些访问造成的数据竞争。
- **race condition（竞态条件）**：算法结果仍可能依赖线程交错，拆开的递增会丢失更新。

所以，结果偶然等于 `2000` 不能说明拆开的版本正确；TSan 不报告，也不能证明算法正确。

我还曾说“并没有两个线程同时读一个共享变量”，这也不是解释工具不报告的理由。并发只读本来就不构成数据竞争，数据竞争的判断也不依赖肉眼观察两条指令是否恰好同一时刻执行。这里真正相关的是：访问是否冲突、是否原子，以及有没有适当的同步关系。

**访问操作有保证，与整个计算逻辑有保证，需要分别检查。**

### 5.3 原子读取不会等其他线程完成

如果两个工作线程各执行一次 `fetch_add(1)`，主线程在等待之前 `load()`，可能读到 `0`、`1` 或 `2`。这里假设计数器从零初始化，而且没有其他写入。

我的最终判断是：

> “不存在data race……只是线程执行的时序会导致输出结果不同,可能输出0,1,2”

这个认识把两种保证分开了：原子操作保证对应访问的原子性；等待线程完成仍需要 `join()` 等机制。若想最终读取到 `2`，先等待两个工作线程结束，再读取。示例中的线程对象也都要得到妥善处理；仍可连接的 `std::thread` 直接析构会触发终止。

## 6. 把四次练习放在一起，我留下哪些检查习惯

| 需要检查的问题 | 这轮练习里的例子 |
|---|---|
| 谁拥有内存，谁只是借用？ | 数组仍归 `owner`，线程拿到借用指针 |
| 被借用对象能活到什么时候？ | 工作结束以前不能释放数组，引用捕获也不能悬空 |
| 各线程具体访问哪里？ | 分段修改不同元素，与共同更新 `total` 不同 |
| 哪里建立同步关系？ | 读取 `left` 前 `join()`，共享更新使用同一把锁 |
| 原子操作的边界是什么？ | `fetch_add` 是整体，拆开的 `load`、`store` 不是 |
| 证据能够支持什么结论？ | `PASS` 验证结果，TSan 检查执行中观察到的竞争，二者都不是完整证明 |

练习 7 的“各算各的，最后合并”、练习 8 的“局部计算，加锁合并”和练习 9 的“原子计数”，并不是后一种出现就淘汰前一种。它们面对不同的共享方式；单个计数器适合原子操作，多个变量之间的整体约束则需要进一步设计，不能机械地把变量全部换成 `atomic`。

从第一篇的析构，到这次 `lock_guard` 的解锁，我开始看到 RAII 在不同资源上的连续性。从练习 5 的分块，到现在的多线程求和，我也开始在空间之外检查时间：**数据在哪，谁在用，什么时候才轮到下一步？**
